# Reward-Preserving Context-Reduction Experiment

## Configuration

This report describes the results currently stored in
`results/reward_preserving_reduction.csv`, generated by
`experiments/reward_preserving_reduction.py`.

- Random seed: `20261018` (`DEFAULT_SEED`)
- Epsilon: `0.1` (`DEFAULT_EPSILON`)
- Context rows are shuffled reproducibly using NumPy's
  `default_rng(seed).permutation(...)`.
- Each case uses a uniform context distribution.
- Actions are `[0, 1]`.
- Rewards are exact values generated by
  `compute_true_expected_rewards`; no sampled or held-out reward estimates
  were used in this run.
- The CSV was generated with the runner's default command configuration.

The cases are:

1. `irrelevant_context`
2. `policy_relevant_context`
3. `interacting_context`
4. `epsilon_tolerance`

## Methods and metrics

The experiment compares:

- `full_context_reference`: retains every context variable and uses the
  full-context optimal policy.
- `prototype_context_reduction`: uses the existing score-threshold
  `reduce_context` prototype, then evaluates the best policy for the selected
  subset using the same grouped-context policy helper as the new method.
- `reward_preserving_backward_elimination`: the greedy backward-elimination
  algorithm, with candidate feasibility determined by the selection reward
  table and the full-context reference reward.

The CSV records:

- `selected_context`: retained variables.
- `context_size`: number of retained variables.
- `reduction_ratio`: fraction of original variables removed.
- `reference_reward`: expected reward of the full-context reference policy.
- `achieved_reward`: expected reward of the method's selected policy.
- `reward_gap`: `reference_reward - achieved_reward`.
- `policy_agreement`: probability-weighted agreement with the reference policy.
- `selection_feasible`: whether the method's result satisfies the configured
  epsilon threshold under the runner's selection/evaluation table.
- `evaluation_within_epsilon`: whether the recorded achieved reward is within
  epsilon of the recorded reference reward.
- `runtime`: measured wall-clock runtime in seconds for the method evaluation.

Because this run uses the same exact reward table for selection and reporting,
`selection_feasible` and `evaluation_within_epsilon` agree in the CSV. This
does not establish unbiased performance for estimated rewards.

## Reward preservation and epsilon outcomes

- `irrelevant_context`: both reduction methods remove all context variables
  and preserve the reference reward exactly (`reward_gap = 0.0`).
- `policy_relevant_context`: the greedy method retains `C` and preserves the
  reference reward. The prototype removes `C`, achieves `0.5` instead of
  `0.8`, and violates epsilon because its `0.3` gap is greater than `0.1`.
- `interacting_context`: both methods retain `A,B` and preserve the reference
  reward exactly.
- `epsilon_tolerance`: the greedy method removes `C` because its measured
  reward gap is `0.050000000000000044`, which is positive and less than or
  equal to the configured epsilon `0.1`. It is therefore feasible while not
  preserving reward exactly. Its policy agreement is `0.5`.

Across the measured rows, the greedy method is feasible in every case. It
achieves exact reward preservation in three cases and uses the configured
slack in the epsilon-tolerance case.

## Exhaustive subset search

No exhaustive subset-search implementation exists in the repository and no
exhaustive-search method appears in the generated CSV. Consequently, this
experiment makes no measured comparison with exhaustive search.

## Limitations and interpretation

- These are small, deterministic synthetic cases with exact structural reward
  tables. They demonstrate behavior of the implementation but do not establish
  causal validity, novelty, or a general policy-preservation guarantee.
- The new method is greedy. It evaluates one-variable removals at each step
  and can miss a globally smallest feasible subset when interactions make a
  different removal sequence necessary.
- The prototype's score assignments are hand-coded per case to expose its
  behavior; they are not causal evidence or a learned feature-selection
  procedure.
- Runtime is machine- and execution-dependent. The values reported here are
  the measured values in the current CSV, not performance guarantees.
- The runner records selection and evaluation feasibility using the same exact
  reward table in this experiment. Separate selection and evaluation reward
  tables are supported by the algorithm but were not used for this CSV.
- The `epsilon_tolerance` result illustrates the intended distinction between
  exact reward preservation and epsilon-feasible reduction: a feasible result
  may have a small nonzero reward gap.
